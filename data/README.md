# Data in this starter

`providers.json` configures the four institutions named in the challenge and now records the planned scrape-and-review mode, seed URLs, bounds and user-confirmed scraping permission. Direct source probes were performed on 14 November 2026. These are discovery links, not invented API endpoints. The source adapters and server host enforcement are still to be implemented; configuration alone does not execute a scraper. See `docs/SCRAPING_PLAN.md`.

`demo-offers.json` contains eight invented activities, two assigned to each provider solely to exercise the prototype. The names, times, prices, age limits, access details and availability are fictional. They are not advertised courses, verified availability or institutional endorsements. Each record has `source.kind = "demo"`, a null record URL, and no verification timestamp. Never remove the visible demo label.

The dates are fixed in November 2026 for reproducible tests. The tests use a fixed reference clock. For a later demonstration, deliberately update the sample dates and repeat the checks. Ordinary application filtering defaults to the real current clock.

`demo-import.json` contains one changed offer and one new offer. It demonstrates a review preview, without fetching or publishing anything. Missing offers in an import never imply deletion.

Consolidated plan revision 3 also specifies a CSV template and a separate fictional 20-row upload demonstration in `docs/IMPORT_WORKFLOW.md`. Umang will create those artifacts and the parser during implementation. They are not part of the current fixture set, and no upload/edit/publication endpoint exists yet. Preserve that distinction in handoffs.

Umang should replace or supplement samples with manually reviewed provider records only when the source supplies those facts. Unknown information stays null. Do not translate an unverified inference into a provider fact. Do not copy school-group activities into family results without evidence of individual access. Provider configuration does not grant authority to publish a record.

`source-runs/<provider>-latest.json` (U1/U2) are real staged runs of the four adapters (aim, experimenta, haus-der-familie, ipai) retrieved on 14 November 2026: provider candidates with field evidence, all `reviewStatus: "pending"` and `verifiedAt: null`. It is a dated snapshot, not a live fetch, and nothing in it is published to `GET /api/offers` until a human approves it through the planned review service. Refresh with `node src/server/scraping/cli.ts --provider all --window-days 180`; a failed refresh keeps the previous snapshot. See `docs/handoffs/UMANG_U1.md` and `UMANG_U2.md`.

`catalog/reviewed-offers.json` is the committed **reviewed baseline**: 17 real records (aim 6, experimenta 1, Haus der Familie 10) approved on 14 November 2026 after an evidence review. Every approved record's own provider page was re-fetched and confirmed to contain its date, start time, title and fee. `catalog/review-decisions.json` records every staged row's decision with reason and quoted evidence: 15 approved, 2 corrected and approved, 14 held. `catalog/review-report.json` is the applied result. Re-apply after a fresh run with `node src/server/review/apply-review.ts`; a row whose source facts changed is held for a fresh review, never approved silently. The public API uses this baseline when no local runtime catalogue (`catalog/published-offers.json`, git-ignored) exists, and `POST /api/admin/reset` restores it. These are dated review results, not live availability; check the provider page before registering.
